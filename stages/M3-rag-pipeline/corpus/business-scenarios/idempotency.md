# 接口幂等设计

## 为什么需要幂等

网络重试、用户重复点击、MQ 重复投递都会导致同一请求到达多次。转账、下单、扣库存这类写操作如果不做幂等，重复请求会造成资金或数据错乱。

## 常见方案

- 数据库唯一索引：以业务单号（订单号、流水号）建唯一键，重复插入直接失败，最简单可靠。
- 防重 Token：进入页面先领一个一次性 token，提交时校验并删除（用 Redis 的 setnx/DEL 原子完成）。
- 状态机：更新带前置状态条件，如 `update orders set status='PAID' where id=? and status='UNPAID'`，影响行数为 0 说明已处理过。
- 分布式锁：单机锁或 Redis 锁兜底，配合上述方案使用，一般不单独作为幂等手段。

## 选型思路

有天然业务单号 → 唯一索引优先；前端交互类提交 → token；状态流转类 → 状态机。核心思想都是"以业务语义定义同一件事的唯一键"。

## 面试常见追问

token 方案为什么要先删后判？——先 DEL 再判断影响结果，把"校验+占位"合并成一次原子操作，避免并发下两个请求都通过校验。
