# M6 平台对比：自研 Spring AI 方案 vs 百炼 / Dify / RAGFlow / Milvus

> 研究型里程碑（无运行时代码）。本文以 **M1–M5 自研能力** 为「自研基线」，横向对比主流 RAG/Agent 平台，沉淀「自研 vs 平台」的选型叙事，目标：面试可复述、分享可引用。
> 说明：百炼一列为本阶段基于官方文档校验后的结论（见第 4 步核对）。

## 1. 对比维度总表（速览）

| 维度 | 自研 Spring AI（=M1–M5） | 百炼（阿里云） | Dify | RAGFlow | Milvus |
|------|------------------------|--------------|------|---------|--------|
| **定位** | 学习/作品集：从零自研全链路 | 一站式托管 LLM 应用平台（模型+知识库+智能体） | 开源 LLMOps / 可视化编排平台 | 开源「深度文档理解」RAG 引擎 | 高性能开源向量数据库 |
| **RAG 检索** | 混合检索（Qdrant 稠密 + 本地 BM25 稀疏）+ RRF 融合 + rerank | 托管知识库检索（向量+关键词**混合检索** + 可选 qwen3-rerank 重排） | 支持（依赖外接向量库） | 强项：模板化文档解析 + 切分 + 检索 | 仅向量存储/检索，需搭配上层 |
| **Agent 编排** | `AgentOrchestrator` 自主 ReAct + 结构性护栏 | 智能体（工作流/对话型），可视化编排 | 强项：可视化 DAG 工作流 / Agent | 基础（偏检索问答） | 不涉及 |
| **知识库/LLM Wiki** | 自研 LLM Wiki（`KnowledgeGraph` 知识图谱 + 页面树 + 增量修订 + `/wiki`） | 托管知识库（上传即索引，支持问答，非图谱化 Wiki） | 知识库 + 基础页面，非图谱 | 知识库以文档为中心 | 不涉及（仅存储） |
| **可观测/成本** | `CostMeter` 成本看板 + Micrometer 计时/计数 + `/actuator/prometheus` | 平台级用量/计费面板 | 基础日志/监控 | 基础 | 自身监控指标，需外部接入 |
| **私有化/合规** | 完全自托管，数据不出域 | 公有云托管为主；企业版/专有版支持私有化（以官方为准），并支持**本地化 Hybrid RAG**（解析/嵌入在本地，仅生成调用百炼，数据不出域） | 支持私有化部署 | 支持私有化部署 | 支持私有化部署 |
| **定制性/可控性** | ★★★★★ 代码级可控 | ★★☆ 受平台边界约束（**RAG 不支持替换底层检索/生成组件**） | ★★★ 可改流程但受框架约束 | ★★★ 偏文档场景定制 | ★★★★ 引擎级可调参 |
| **TCO** | 低（学习期近乎零成本，人力为主） | 按量付费，规模上来成本可见 | 自托管硬件+运维，或云服务 | 同 Dify | 同 Dify（向量集群成本） |
| **学习曲线** | 高（要懂全栈细节） | 低（开箱即用） | 中（学会编排即可） | 中（文档管线概念） | 中（向量检索概念） |

## 2. 逐平台剖析

### 2.1 自研 Spring AI 方案（=M1–M5，你的基线）
- **检索**：`HybridSearcher`（Qdrant 稠密 + 本地 BM25 稀疏）→ RRF 融合 → `Reranker`（qwen rerank）精排。
- **生成/问答**：`PipelineService` → `AnswerService`，带引用溯源（`Citation`）。
- **Agent**：`AgentOrchestrator.runStream` 自主 ReAct + 结构性护栏（模型未真实调用工具时强制一次真实检索兜底）。
- **工程化**：SSE 双实时推送、`SemanticCache` 语义缓存、`CostMeter` 成本看板、Micrometer 可观测。
- **评估**：双 RAGAS（Java `LLMJudgeService` 即时代理分 + Python `ragas_eval.py` 真 RAGAS 离线评估）。
- **知识库演进**：LLM Wiki（`EntityExtractor` 抽取实体/关系 → `KnowledgeGraph` 图谱+页面树 → 重入库 merge 增量修订 → `/wiki` 浏览式 UI）。
- **优**：全链路代码级可控，最能体现代码功力，面试有「讲得清每一行」的底气。
- **劣**：所有能力都要自己搭，生产级稳定性/多租户/权限需额外投入。

### 2.2 百炼（阿里云）
- 一站式托管：模型服务（通义千问等）+ **知识库 RAG** + **托管智能体** + 应用编排（AppFlow）。
- 你本项目**已深度使用**百炼作为模型与 Embedding/Rerank 底座（`dashscope` 端点、qwen3.8-27b / qwen3.7-text-embedding-flash / qwen3.7-text-rerank）。
- **知识库（RAG 核心载体）**：支持文档搜索（**向量+关键词混合检索**）、数据查询（NL2SQL）、图片问答、音视频搜索；Embedding 默认 `text-embedding-v4`、重排支持 `qwen3-rerank`；参数含切片长度、TopK、相似度阈值、最大召回数（`wiki/guides/knowledge-base.md`）。
- **托管智能体（managed agents）**：声明式（YAML/API）定义、多步推理 + 工具调用（HTTP/retrieval/函数），`max_iterations` 默认 15、范围 1–50；与平台模型深度集成（`wiki/guides/managed-agents.md`）。
- **生态**：支持 MCP（模型上下文协议），知识库可经 MCP 注入 AgentScope 等框架；也支持 Dify/Coze/n8n/LangChain 经 DashScope API 接入。
- **本地化 Hybrid RAG**：可在本地完成解析/嵌入、仅把检索结果与 query 发百炼生成，实现**数据不出域 + 模型能力复用**（`wiki/concepts/rag.md`）。
- **硬约束（关键差异点）**：百炼 RAG 由平台统一引擎托管，**不支持替换底层检索或生成组件**（自定义向量库或外部 LLM 不可），检索/重排/生成模型均须从平台选项配置（`wiki/concepts/rag.md`）。
- **与自研的关系**：百炼是「平台层」，自研方案是「应用层」；二者并不互斥——完全可用百炼托管模型 + 自研编排/检索/评估/Wiki。
- **适用**：想快速交付业务应用、不想养检索/重排工程团队时。

### 2.3 Dify
- 开源 LLMOps 平台，核心是**可视化 DAG 工作流**与 Agent 编排，知识库/模型/工具插件生态成熟。
- 等价映射：`AgentOrchestrator` 的可视化版；其知识库 ≈ 你的 `IngestionService` + 向量检索；其「知识库 + 基础页面」≈ 你的 `/wiki` 的简化版（但非图谱化）。
- **特点**：生态广、社区活跃、可私有化；强在「业务人员也能搭应用」。
- **适用**：企业内部快速搭建多类 LLM 应用、需要可视化协作时。

### 2.4 RAGFlow
- 开源、以「**深度文档理解**」为核心的 RAG 引擎：内置多种文档模板（PDF/Word/表格/简历…）做结构化解析与智能切分。
- 等价映射：`MarkdownSectionParser` + `TextChunker` 的「模板化增强版」；其强项在解析质量，而非编排。
- **特点**：解析质量高、 hallucination 控制较好；Agent/编排能力弱于 Dify。
- **适用**：文档类型复杂、解析质量是瓶颈的场景（合同、研报、扫描件）。

### 2.5 Milvus
- 高性能开源向量数据库（分布式、十亿级向量），常与上述平台组合（Dify/RAGFlow 的可选向量后端之一）。
- 等价映射：≈ 你的 **Qdrant 层**（都用 gRPC、都支持余弦/欧氏、都支持集群）。
- **特点**：规模与生态极强；但只是「检索底座」，需搭配上层才有 RAG/Agent 能力。
- **适用**：向量规模极大、需要精细调参与集群治理时（Qdrant 在中小规模更轻量）。

## 3. 与 M5 自研能力逐项映射

| M5 自研能力 | 平台等价物 | 备注 |
|------------|-----------|------|
| `HybridSearcher`（稠密+稀疏+RRF） | Dify/RAGFlow 知识库检索；百炼托管检索 | 自研可控性最高 |
| `Reranker`（qwen rerank） | 各平台重排（百炼/Dify 内置） | 思路一致 |
| `AgentOrchestrator` 自主 ReAct | Dify 工作流 / 百炼智能体 | 自研=代码级，平台=可视化 |
| `SemanticCache` 语义缓存 | 多数平台无显式等价（需自建） | 自研的差异化优势 |
| `CostMeter` 成本看板 | 百炼计费面板 / 平台监控 | 自研可细分到 stage |
| 双 RAGAS 评估 | 平台多偏弱或需外接 | 自研的差异化优势 |
| **LLM Wiki 知识图谱** | 各平台知识库（非图谱化） | 自研独有能力，最体现「知识演进」 |
| Qdrant 向量层 | **Milvus**（或平台托管向量） | 可互换 |

> 关键洞察：**自研最值钱的不是「重复造检索」，而是 `SemanticCache`、双 RAGAS 评估、LLM Wiki 这类平台「不自带或不强调」的能力**——这正是面试区分度所在。

## 4. 百炼官方能力核对（已校验）
已基于百炼官方文档核对（来源：`wiki/guides/knowledge-base.md`、`wiki/guides/managed-agents.md`、`wiki/concepts/rag.md`）：

- **知识库=RAG 核心载体**：文档搜索为**向量+关键词混合检索**，重排可用 `qwen3-rerank`；并支持数据查询（NL2SQL）、图片问答、音视频搜索；Embedding 默认 `text-embedding-v4`。
- **托管智能体**：声明式（YAML/API）定义、多步推理 + 工具调用，`max_iterations` 默认 15（1–50）；模型白名单为 qwen-max/plus/turbo。
- **RAG 不可替换底层组件**：平台统一引擎托管，**不支持自定义向量库或外部 LLM**，检索/重排/生成模型均须从平台选项配置——这是与「全栈自研」最本质的边界差异。
- **本地化 Hybrid RAG**：本地解析/嵌入 + 百炼生成，可做到数据不出域；同时支持 MCP，知识库可注入 AgentScope 等框架，也支持 Dify/Coze/n8n/LangChain 经 DashScope API 接入。

> 结论：百炼与自研「非对立、可组合」。自研的差异化价值在平台不强调处——语义缓存、双 RAGAS 评估、LLM Wiki 知识演进、以及对检索/重排/生成组件的完全可控。

## 5. TCO 笔记（自托管 vs 托管）
- **自托管（Dify/RAGFlow + Milvus + 自研）**：一次性硬件/云资源 + 持续运维人力 + 研发人力；规模越大边际成本越低，数据完全可控；适合长期、合规敏感、定制深。
- **托管（百炼等）**：零运维起步、按量付费；业务初期成本低、上线快；规模大后 API 调用费可观，且受平台能力/合规边界约束。
  - 百炼知识库计费（已核对 `wiki/guides/knowledge-base.md`）：**标准版**固定 1 QPS、含 720 小时免费额度；**旗舰版**按 RCU 弹性伸缩（1 RCU ≈ 50 QPS），约 0.2 元/RCU/小时；外加模型 token 调用费。选型时容量档位直接决定成本曲线。
- **学习期**：本项目近乎零成本（本地 Qdrant + 百炼按量，且用量小）。
- **企业落地 TCO 要点**：模型调用费、向量集群/存储费、运维人力、合规改造、扩容弹性。能讲清这五项即达「企业级对齐」。

## 6. 决策框架（Build vs Buy）
- **选平台（Buy）当**：要快上线、团队缺检索/重排工程力、场景标准、合规可接受公有云。
- **选自研（Build）当**：需代码级可控、数据不出域、有差异化能力（缓存/评估/知识图谱）、要作为技术资产/面试作品。
- **混合（推荐）**：用百炼托管模型 + 自研编排/检索/评估/Wiki——取「模型稳定」与「应用可控」之长。

**一句话电梯演讲**：
> "我既能在 Dify/百炼上 1 小时搭出业务应用，也能从零自研一套可控的 RAG/Agent 引擎——因为我知道每一层在做什么；我的作品集就是用 Spring AI 把检索、缓存、成本、评估、知识图谱全链路打通，这正是平台‘开箱即用’背后被抽象掉的部分。"

## 7. 面试要点（可复述）
1. 自研 vs 平台不是对立，是分层：平台在应用层，自研在应用+部分底座层，可组合。
2. 自研的差异化价值在平台不强调处：语义缓存、双 RAGAS 评估、LLM Wiki 知识演进。
3. 向量库可互换（Qdrant↔Milvus），真正壁垒在「检索融合/重排/评估/知识建构」的工程细节。
4. TCO 五项（模型/存储/运维/合规/扩容）能随口而出。
